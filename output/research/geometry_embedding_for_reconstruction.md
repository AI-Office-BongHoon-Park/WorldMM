# Geometry embeddings for reconstructable spatial memory

_Date: 2026-05-22 KST. Scope: methods that can store scene/object geometry as retrievable latent or compact state, then decode/render/reconstruct at recall time. Constraint: no package installs; evidence from papers + GitHub source/README permalinks where available._

## Executive read

WorldMM currently stores text triples in 384-d MiniLM vectors. Geometry-aware memory needs two channels:

1. **Retrieval vector**: small ANN key, e.g. text/CLIP/scene descriptor.
2. **Reconstructable sidecar**: larger latent/state blob, e.g. point tokens, triplane, SDF code, Gaussian set, pointmap, or structured scene tokens.

Best fit is not “append one 384-d vector and expect full 3D back.” Best fit is **append one retrieval vector + sidecar pointer/hash**. The sidecar holds reconstructable geometry state. Retrieval returns triple + sidecar; decoder reconstructs 3D.

Shortlist:

1. **Compressed 3D Gaussian Splat sidecar**: scene-scale, renderable, explicit, closest to “recall original scene.” Compact3D/LightGaussian reduce size while preserving rendering. Store ANN key + compressed Gaussian file pointer.
2. **TripoSR/OpenLRM triplane sidecar**: object-level or small-scene feedforward latent. Store image/text key + triplane; decode density/color to mesh/render.
3. **Shap-E / SDF-style latent sidecar**: compact per-object latent, directly decodable to mesh/images. Good for object memories, less for exact real scene recall.

DUSt3R/MASt3R/VGGT are strong capture front-ends: cache their pointmaps/depth/camera outputs as sidecars, but they are geometry predictions, not compact learned scene codes. OpenScene/LERF/LangSplat add language retrieval to 3D fields; they are excellent retrieval overlays but usually not sufficient alone to reconstruct high-fidelity geometry unless paired with the underlying NeRF/3DGS.

## Design implications for WorldMM

### 1. Separate retrieval key from reconstructable payload

A 384-d MiniLM vector can retrieve “mug on left side of desk,” but cannot hold a reconstructable 3D scene. Add fields:

```json
{
  "triple": "mug left-of keyboard on desk",
  "text_vec_384": "...",
  "geom_key_vec": "optional CLIP/MASt3R/OpenScene vector",
  "geom_payload_type": "compact3dgs|triplane|sdf|pointmap|scenescript",
  "geom_payload_uri": "sha256://... or local/object-store path",
  "geom_decoder": "compact3d@dccc07e|triposr@d26e331|shap-e@5013101",
  "pose_frame": "worldmm_scene_A1_JAKE_DAY1",
  "bbox_or_anchor": [x, y, z, dx, dy, dz]
}
```

### 2. Use tiered sidecars

- **Fast recall**: text triple + 384-d vector + bbox/pose.
- **Geometry recall**: point cloud / pointmap / compact 3DGS sidecar.
- **Semantic recall**: OpenScene/LangSplat features aligned to 3D positions.
- **Parametric layout recall**: SceneScript tokens for room-level structure.

### 3. Avoid hallucinated reconstruction for observed memory

Generative latents (DreamFusion, Shap-E, Point-E, GET3D, SDFusion) are useful when memory target is category/object prior. For “reconstruct original scene at recall,” prefer observed-state representations: **3DGS/Compact3D, DUSt3R/VGGT pointmaps, SceneScript layout, DeepSDF only for scanned objects**.

## Shortlist of 3

### 1) Compact/Light 3D Gaussian sidecar + language feature overlay

- **Why**: stores actual radiance geometry; decoder is renderer; compressed variants reduce storage; LangSplat can add language retrieval.
- **WorldMM pattern**: append `geom_payload_uri` to triple; ANN key from text/CLIP; retrieve compressed `.ply`/checkpoint and render.
- **Risk**: payload variable-size and scene-specific; license of official 3DGS/LightGaussian needs review; 6GB feasible only for small/compressed scenes.
- **Best implementation path**: start with small scene chunks, Compact3D quantized PLY, optional LangSplat features.

### 2) TripoSR/OpenLRM triplane sidecar for object memories

- **Why**: feedforward from single image; triplane is a real latent; decoder reconstructs mesh/renders via density/color MLP.
- **WorldMM pattern**: store object crop image embedding as retrieval key + triplane tensor as sidecar.
- **Risk**: object-centric, not exact scene capture; input viewpoint ambiguity.
- **Best implementation path**: per-object memories from egocentric frames; use triplane to reconstruct object proxy at recall.

### 3) Shap-E / DeepSDF latent for compact object geometry

- **Why**: compact latent code decodes to mesh/implicit surface. DeepSDF is clean if shape code is optimized from scan; Shap-E is easier generative decoder.
- **WorldMM pattern**: triple points to latent vector file; retrieve by semantic key; decode mesh on demand.
- **Risk**: object-level only; generative methods may hallucinate, DeepSDF needs per-object fitting.
- **Best implementation path**: use for canonical object instances and affordance geometry, not full room memory.

## Bottom line

For WorldMM “spatial memory that reconstructs at recall,” store **retrieval vector + reconstructable sidecar**, not one vector. Use:

1. **Compressed 3DGS** for faithful scene chunks.
2. **Triplane LRM/TripoSR** for fast object 3D proxies.
3. **SDF/Shap-E/DeepSDF** for compact object shape codes.

Add **OpenScene/LangSplat/MASt3R descriptors** as semantic-geometric retrieval layers. Keep VGGT/DUSt3R as front-end geometry producers; cache their outputs, but do not treat their ANN descriptor alone as reconstructable memory.
